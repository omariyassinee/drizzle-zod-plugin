# Declarative Error Mapping for `refineSchema`

**Target package:** `@vacuus/drizzle-validators`  
**Primary files:** [`packages/drizzle-validators/src/refine.ts`](/home/null/Space/Project/drizzle-zod-plugin/packages/drizzle-validators/src/refine.ts), [`packages/drizzle-validators/src/zod-compat.ts`](/home/null/Space/Project/drizzle-zod-plugin/packages/drizzle-validators/src/zod-compat.ts)  
**Status:** Design only; no implementation is included in this proposal.

## 1. Objective

Add two declarative overloads to the existing Zod `refineSchema` API:

```ts
refineSchema(baseSchema, errorMap);
refineSchema(baseSchema, refinementFn, errorMap);
```

The second form must keep the callback before the map. This is intentional: TypeScript infers the callback result from left to right, so the fallback map can see fields added by the callback and can use the callback's replacement schema types.

The feature is a fallback stylesheet, not a message replacement mechanism. An inline Zod error such as:

```ts
z.number().min(18, { error: "Custom inline" })
field.setError("Custom inline")
```

always wins over the fallback map.

The design applies to every Zod validator generated by the package, including string, number, bigint, boolean, date, array, tuple, enum/literal, object, JSON/unknown, nullable/optional/default/catch/readonly, and custom refinements. Valibot and TypeBox remain separate validator backends: they should expose equivalent public concepts through their own adapter APIs, but Zod internal AST objects must never be inspected by those backends.

## 2. Public API

### 2.1 Error keys

Use the Zod 4 issue vocabulary as the canonical public key set. Keep aliases only where they improve ergonomics; do not make aliases the runtime source of truth.

```ts
export type ErrorMapKey =
  | "invalid_type"
  | "invalid_value"
  | "too_small"
  | "too_big"
  | "invalid_format"
  | "not_multiple_of"
  | "unrecognized_keys"
  | "invalid_union"
  | "invalid_key"
  | "invalid_element"
  | "custom";

export type CheckErrorKey =
  | "min"          // too_small: min_length, greater_than
  | "max"          // too_big: max_length, less_than
  | "length"       // exact length
  | "format"       // string_format and top-level format
  | "regex"
  | "starts_with"
  | "ends_with"
  | "includes"
  | "multiple_of"
  | "int"           // number_format
  | "custom";
```

`ErrorMapKey` is useful for issue-wide defaults. `CheckErrorKey` is useful for the more specific check type. A field map may provide both; dispatch first looks for the specific key, then the issue key, then a type-wide default.

### 2.2 Core categorisation

The map must be constrained by the *deeply unwrapped core* rather than by the outer optional/nullable/default wrappers.

```ts
type StringErrorKey =
  | "invalid_type" | "invalid_value" | "too_small" | "too_big"
  | "invalid_format" | "custom";

type NumberErrorKey =
  | "invalid_type" | "invalid_value" | "too_small" | "too_big"
  | "not_multiple_of" | "custom";

type BigIntErrorKey = NumberErrorKey;
type DateErrorKey = NumberErrorKey;
type ArrayErrorKey =
  | "invalid_type" | "invalid_value" | "too_small" | "too_big"
  | "invalid_element" | "custom";
type SetErrorKey = ArrayErrorKey;
type EnumErrorKey = "invalid_value" | "invalid_type" | "custom";
type LiteralErrorKey = EnumErrorKey;
type ObjectErrorKey =
  | "invalid_type" | "invalid_value" | "unrecognized_keys"
  | "invalid_key" | "invalid_element" | "invalid_union" | "custom";
type GenericErrorKey = ErrorMapKey;

export type FieldErorMapForCore<
  TCore extends z.ZodTypeAny,
> = Partial<Record<AllowedErrorKeyForCore<TCore>, string>>
  & ErrorMapOptions;
```

`FieldErorMapForCore` intentionally preserves the requested spelling for compatibility with the design brief. The implementation should also export the correctly spelled alias:

```ts
export type FieldErrorMapForCore<TCore extends z.ZodTypeAny> =
  FieldErorMapForCore<TCore>;
```

`AllowedErrorKeyForCore<T>` is a conditional type over `DeepUnwrap<T>`:

```ts
type AllowedErrorKeyForCore<T extends z.ZodTypeAny> =
  DeepUnwrap<T> extends z.ZodString ? StringErrorKey :
  DeepUnwrap<T> extends z.ZodNumber ? NumberErrorKey :
  DeepUnwrap<T> extends z.ZodBigInt ? BigIntErrorKey :
  DeepUnwrap<T> extends z.ZodDate ? DateErrorKey :
  DeepUnwrap<T> extends z.ZodArray<any> ? ArrayErrorKey :
  DeepUnwrap<T> extends z.ZodSet<any> ? SetErrorKey :
  DeepUnwrap<T> extends z.ZodEnum<any> ? EnumErrorKey :
  DeepUnwrap<T> extends z.ZodLiteral<any> ? LiteralErrorKey :
  DeepUnwrap<T> extends z.ZodObject<any> ? ObjectErrorKey :
  GenericErrorKey;
```

Do not use `any` to make the conditional map accept arbitrary keys. Unknown or future Zod core types should receive `GenericErrorKey`, while unknown issue/check values at runtime must fail closed as described below.

### 2.3 Field and schema maps

```ts
export interface ErrorMapOptions {
  /** Used when no specific issue/check entry is present. */
  default?: string;
  /**
   * Optional issue-aware escape hatch. Returning undefined means "continue
   * normal fallback dispatch"; it never suppresses an inline schema error.
   */
  error?: (issue: z.core.$ZodIssue, ctx: ErrorMapContext) => string | undefined;
}

export type FieldErrorMap<TField extends z.ZodTypeAny> =
  FieldErrorMapForCore<TField>;

export type SchemaErrorMap<
  TShape extends Record<string, z.ZodTypeAny>,
> = {
  [K in keyof TShape]?: FieldErrorMap<TShape[K]> | string;
} & {
  /** Applies to fields added by a refinement callback. */
  [field: string]: FieldErrorMap<z.ZodTypeAny> | string | undefined;
};
```

`string` is a shorthand for `{ default: string }`. It is not a wildcard that replaces inline errors.

The map may also reserve an object-level entry without weakening field inference:

```ts
type ObjectErrorMap<TShape> = SchemaErrorMap<TShape> & {
  _object?: Partial<Record<ErrorMapKey, string>> | string;
};
```

Whether `_object` is exposed in the first release should be decided before implementation. If omitted, object-level checks continue using their existing inline errors and no field map is applied to them.

### 2.4 Required overload order

The overloads should be declared in this order:

```ts
export function refineSchema<
  T extends z.ZodObject<any>,
  TMap extends SchemaErrorMap<T["shape"]>,
>(baseSchema: T, errorMap: TMap): /* mapped object schema */;

export function refineSchema<
  T extends z.ZodObject<any>,
  R extends RefinementCallbackResult<T["shape"]>,
  TMap extends SchemaErrorMap<RefinedShape<T["shape"], R>>,
>(
  baseSchema: T,
  refinementFn: (fields: RefinableShape<T["shape"]>) => R,
  errorMap: TMap,
): /* mapped object schema */;
```

The callback overload must not be written as `(base, map, callback)`, nor should the map be hidden in a generic inferred before `R`. `RefinedShape<T, R>` must include callback-added keys and use `ResolveRefinedField` for replaced keys. The implementation signature can use `unknown`/internal types, but the public overloads must preserve the inferred schema output.

## 3. Type inference examples

```ts
const result = refineSchema(
  base,
  (fields) => ({
    age: fields.age.min(18),
    displayName: z.string().min(1),
  }),
  {
    age: { too_small: "Must be an adult" },
    displayName: { too_small: "Required" }, // callback-added field is known
  },
);
```

Changing `age` from a number schema to a string schema in the callback must cause the map entry to be checked against the string category. A map key valid for the old core but not the new core should be a TypeScript error.

The error-only overload maps the original shape:

```ts
refineSchema(base, {
  email: { invalid_format: "Enter a valid email" },
  age: { too_small: "Too young" },
});
```

## 4. Runtime architecture

### 4.1 Keep the existing immutable pipeline

The implementation should reuse:

- `unwrapAll` / `applyWrappers` in [`refine.ts`](/home/null/Space/Project/drizzle-zod-plugin/packages/drizzle-validators/src/refine.ts).
- `cloneSchemaWithDef`, `cloneZodCheck`, `getZodDef`, and `rebuildZodObject` in [`zod-compat.ts`](/home/null/Space/Project/drizzle-zod-plugin/packages/drizzle-validators/src/zod-compat.ts).
- `UNWRAP_PROXY` so proxies never enter the final object shape.
- `rebuildZodObject` so strict, loose, catchall, object-level checks, and descriptions survive.

Do not assign to `_zod.def`, `_def`, `checks`, or `error` on a base schema. Every changed definition and every changed check must be cloned with its original constructor. This is the C1 non-contamination guarantee: applying a map to one refined schema cannot alter the base schema or another schema derived from it.

Suggested internal stages:

1. Validate overload arguments and normalise a string map entry to `{ default }`.
2. Run the callback, if present, using the existing lazy field proxy.
3. Assemble the output shape exactly as today, resolving branded proxies and raw replacements.
4. For every output field with a map entry, call `applyFallbackErrorMap(field, mapEntry)`.
5. Rebuild the object using `rebuildZodObject`.

The map is applied after callback replacements. Therefore it sees the final schema and its final core type.

### 4.2 Error precedence

There are three distinct sources of messages:

1. Inline check/schema errors (`.min(..., { error })`, `.setError(...)`, `z.string({ error })`).
2. The fallback map.
3. Zod's built-in default message.

The required order is 1 > 2 > 3. Never set an unconditional fallback function that replaces an existing `error` property.

For each schema definition and check:

- If `def.error` is already present, preserve it byte-for-byte.
- If `checkDef.error` is already present, preserve it byte-for-byte.
- Otherwise clone the definition/check and add a fallback error function.
- The fallback function may return `undefined`; that delegates to Zod's default message.

This is important for `.setError()`: the existing helper recursively clones schemas and checks with `error: () => message`. The mapper must detect those properties and leave them untouched.

### 4.3 Issue and check dispatch

Zod 4 emits broad issue codes while the internal check definition identifies the exact operation. Use both:

```ts
interface ErrorMapContext {
  field: string;
  coreType: string;
  check?: string;
  format?: string;
  schema: z.ZodTypeAny;
}
```

Dispatch algorithm:

1. Identify `issue.code`.
2. Identify the originating check from `issue.inst` where available, or from the cloned check closure's captured check definition.
3. For `too_small`:
   - `min_length` -> `min`
   - `length_equals` -> `length`
   - numeric/date/bigint `greater_than` -> `min`
   - array/set minimum -> `min`
4. For `too_big`:
   - `max_length` -> `max`
   - numeric/date/bigint `less_than` -> `max`
5. For `invalid_format`:
   - `string_format` with `format === "regex"` -> `regex`
   - `starts_with`, `ends_with`, `includes` -> corresponding specific key
   - all other string formats (`email`, `url`, `uuid`, `datetime`, etc.) -> `format`
6. `not_multiple_of` -> `multiple_of`.
7. `invalid_type`, `invalid_value`, `unrecognized_keys`, `invalid_union`, `invalid_key`, `invalid_element`, and `custom` use their issue keys.
8. Lookup order:
   - specific check key;
   - broad issue code;
   - `default`;
   - `undefined`.

The runtime must support both Zod 4's current `issue.inst` shape and definitions where the originating check is available only through the closure. Avoid relying on one undocumented property without a guarded fallback.

Unknown issue codes and unknown check types must not silently map to a generic message. They should skip the map and allow Zod's standard error, unless the package's existing error policy requires throwing for unsupported internal definitions. For schema cloning, an unknown check should produce an actionable `DrizzleValidatorsError`, matching the current `transferChecks` fail-loud behavior.

### 4.4 Installing fallback functions without mutation

Implement a helper in `refine.ts` or a small internal module:

```ts
function applyFallbackErrorMap(
  schema: z.ZodTypeAny,
  field: string,
  map: string | FieldErrorMapForCore<z.ZodTypeAny>,
): z.ZodTypeAny;
```

The helper should:

- unwrap the field only for core classification;
- recursively clone `innerType` and `element`, preserving wrappers and lazy default/catch accessors;
- clone `checks` and install a fallback only on checks lacking `error`;
- install a fallback on the core definition only when `def.error` is absent;
- preserve all unrelated definition keys;
- return the same schema only when no map entry exists or no definition needs changing.

A closure may capture a normalised immutable map and context, but it must not capture mutable schema definitions. The closure should return `string | undefined`, as required by Zod 4 error customization.

Do not call `.check()` to add fallback checks. Error mapping is message customization, not a validation rule, and adding checks changes parse behavior.

## 5. AST dispatch details

### 5.1 Core classification

Use the existing `getZodDef` and `unwrapAll` helpers. Core `def.type` values are the runtime classification source:

| Core family | Zod definition type | Relevant checks |
|---|---|---|
| string | `string` | `min_length`, `max_length`, `length_equals`, `string_format` |
| number | `number` | `greater_than`, `less_than`, `multiple_of`, `number_format` |
| bigint | `bigint` | `greater_than`, `less_than`, `multiple_of` |
| date | `date` | `greater_than`, `less_than` |
| array | `array` | `min_length`, `max_length`, `length_equals` |
| set | `set` | `min_size`, `max_size`, or equivalent Zod check metadata |
| enum/literal | `enum`, `literal` | `invalid_value` |
| object | `object` | object issues and custom checks |
| union | `union`, `discriminated_union` | `invalid_union`, `invalid_value` |
| other | all remaining types | generic issue keys |

The dispatch must tolerate check metadata differences between Zod patch versions. Check matching should use explicit guarded fields (`check`, `format`, `minimum`, `maximum`, `value`, `length`) and not assume every check exposes all fields.

### 5.2 Format aliases

Zod 4 formats may be represented by a top-level `def.format` or a `string_format` check. Treat both as `invalid_format`; use the format name only to select `regex`, `starts_with`, `ends_with`, `includes`, or the general `format` key.

This avoids hardcoding every present and future Zod string format. New formats automatically use `format` unless a dedicated dispatch rule is added.

### 5.3 Arrays and nested schemas

A field map applies to the field's own issues. For `z.array(z.string())`, the array field map controls array length/type errors; element string errors remain governed by the element schema's inline errors or a future nested-map facility. Do not apply a parent field's string map recursively to elements: that would incorrectly classify `invalid_element` and could alter unrelated messages.

The cloning traversal may recurse through `element` to preserve an existing inline `.setError()` implementation, but fallback installation should be explicit about scope. A future nested syntax can be added without changing the top-level map contract.

## 6. Compatibility with all package validators

`refineSchema` currently accepts a Zod object and returns a Zod object. The new overloads therefore belong in the Zod refine entry point and must not import Valibot or TypeBox runtime code.

The package's validator-neutral architecture should nevertheless define an adapter contract for parity:

```ts
interface ValidatorErrorMappingAdapter<TSchema, TMap> {
  applyErrorMap(schema: TSchema, map: TMap): TSchema;
}
```

- Zod: implement the AST cloning and issue dispatch described here.
- Valibot: use its pipe/action issue metadata and immutable schema/action reconstruction.
- TypeBox: map error output at the checker/formatter boundary; do not pretend TypeBox has Zod checks.

The generated Drizzle schemas for all three backends should remain valid without importing this Zod-only module. Shared public documentation can describe the same precedence rule, but backend-specific key availability must be typed against each backend's actual error model.

## 7. Edge cases and policy decisions

1. **Unknown map field:** Throw a `DrizzleValidatorsError` with the field name, unless the project intentionally permits maps for future callback-added keys. The callback overload must permit callback-added fields; the error-only overload should reject misspelled base fields at compile time and validate at runtime.
2. **Undefined map value:** Treat it as absent. Do not install a fallback.
3. **Empty string:** Valid explicit message; do not treat it as absent.
4. **Map callback throws:** Let the error propagate. Do not catch and convert it into a success-shaped schema.
5. **Async refinement:** Error mapping is synchronous schema construction and does not change `parse` versus `parseAsync` requirements.
6. **Transforms/codecs/pipes:** Classify the outer schema when it has issues; recurse only where Zod definitions explicitly expose an inner schema. Do not rebuild a transform by guessing its internal shape.
7. **Defaults/catch:** Preserve lazy getters using the existing constructor/accessor path in `zod-compat.ts`.
8. **Strict/loose/catchall objects:** Rebuild through `rebuildZodObject`; maps must not change unknown-key policy.
9. **Shared schemas:** Every changed check and definition is cloned. Add contamination tests that parse the original base after mapping and compare its errors.
10. **Object-level refinement:** Do not accidentally apply a field map to an object-level custom issue whose path is empty. Support an explicit `_object` policy only if product requirements call for it.
11. **Zod version drift:** Keep all `_zod.def` access behind `zod-compat.ts`; add narrow guards and tests for the supported Zod 4 range.

## 8. Test plan

Add focused tests to `refine-schema.test.ts` and the existing contamination/wrapper suites:

### Type tests

- Error-only map infers keys from the base shape.
- Callback map sees callback-added fields.
- Callback replacement from number to string changes allowed map keys.
- Invalid field/check keys fail compilation.
- String shorthand is accepted.
- `FieldErorMapForCore` and `FieldErrorMapForCore` remain equivalent.

### Runtime tests

- `invalid_type`, `invalid_value`, `too_small`, `too_big`, `invalid_format`, `not_multiple_of`, and `custom`.
- `min_length`, `max_length`, `length_equals`, `greater_than`, `less_than`, `string_format`, `regex`, `starts_with`, `ends_with`, and `includes`.
- Inline `.min(..., { error })` beats the map.
- `.setError()` beats the map.
- Map fills only missing errors and falls back to Zod defaults when no entry exists.
- Email/UUID/URL and future-like unknown string formats use `format`.
- Arrays distinguish array length errors from element errors.
- Optional, nullable, default, catch, readonly, strict, loose, catchall, union, enum, literal, date, bigint, and custom refinements.
- Base schema definitions and checks are unchanged after both overloads.
- Multiple mapped outputs made from the same base do not contaminate one another.
- Existing two-argument callback API remains unchanged.
- Invalid argument order and non-function callback produce the existing actionable errors.

Run the smallest relevant suite first, then package typecheck/build:

```sh
bun test packages/drizzle-validators/tests/refine-schema.test.ts
bun test packages/drizzle-validators/tests/bug-repro/refine-contamination.test.ts
bun run --filter='@vacuus/drizzle-validators' typecheck
bun run --filter='@vacuus/drizzle-validators' build
```

## 9. Implementation sequence

1. Add public type aliases and conditional core-key mappings without changing runtime behavior.
2. Add the two overload signatures and an internal argument normaliser.
3. Add issue/check dispatch helpers with table-driven tests.
4. Add immutable fallback installation using `cloneSchemaWithDef` and `cloneZodCheck`.
5. Apply maps after callback result resolution and before `rebuildZodObject`.
6. Add contamination, precedence, wrapper, and type-inference tests.
7. Update the refine entry-point documentation and package API declaration output.
8. Validate Zod, Valibot, and TypeBox build surfaces to ensure the Zod-only types do not leak into other adapters.

The central acceptance criterion is that the map is a type-safe default stylesheet over the final callback-produced schema, while inline errors and the original schema remain authoritative and untouched.
